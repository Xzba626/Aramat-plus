## 1. Назначение модуля

Раздел управляет **всеми торговыми точками** компании.

Он **не хранит товары самостоятельно**. Товары поступают только из **Центрального склада** (№16).

Каждая точка имеет:

- собственную историю;
- собственные остатки (для филиала) или остатки склада (для Owner Direct);
- собственных сотрудников (филиал);
- собственную аналитику.

Все действия **полностью журналируемы**.

## 2. Список торговых точек

После открытия раздела владелец видит **все** точки.

**Порядок:** сначала ⭐ **Личные продажи владельца** (`OWNER_DIRECT`), затем филиалы (`BRANCH`).

### Обязательные поля карточки филиала

| Поле | Обязательно |
|------|-------------|
| Название | ✅ |
| Статус: Работает / Закрыт / На ревизии | ✅ |
| Адрес | ✅ |
| Количество сотрудников | ✅ |
| Количество различных товаров (SKU) | ✅ |
| Общее количество единиц товара | ✅ |
| Остаточная стоимость товара (по себестоимости FIFO/партий на точке) | ✅ |
| Продажи за сегодня | ✅ |
| Продажи за месяц | ✅ |
| Текущая прибыль (период: сегодня; месяц — на карточке или в обзоре) | ✅ |

Карточка открывается **одним нажатием**.

Карточка **Owner Direct** — по [№17](owner-direct-sales.md): источник = склад, без перемещений, KPI продаж канала.

## 3. Вкладки внутри точки (не длинная страница)

Каждая вкладка работает **независимо** (`?tab=` или nested routes).

### Филиал (`BRANCH`)

```
Обзор
Остатки
Продавцы
История продаж
История скидок
История возвратов
История ревизий
Запросы
Настройки
```

### Owner Direct (`OWNER_DIRECT`)

```
Обзор
Остатки склада
История продаж
История скидок
История возвратов
Запросы
POS / Продажа
Настройки канала
```

(без «Продавцов филиала» и без «Истории ревизий филиала» как у BRANCH — ревизии склада живут в модуле склада/ревизий).

---

## 4. Вкладка «Обзор»

Краткая сводка, **без длинных таблиц**:

- название, статус, адрес;
- дата открытия;
- ответственный менеджер;
- количество продавцов;
- количество товаров (SKU);
- продажи сегодня;
- прибыль сегодня;
- прибыль месяца;
- средний чек;
- последний вход сотрудников;
- последняя ревизия.

---

## 5. Вкладка «Остатки»

Все товары **этой** точки (для Owner Direct — остатки **центрального склада**).

По каждому товару:

- фото (бренд);
- название, бренд, категория;
- остаток, единица;
- минимальный остаток;
- цена продажи;
- статус: **Нормально** / **Заканчивается** / **Закончился**.

Обязательно: поиск · фильтрация · сортировка · пагинация.  
Ниже порога — подсветка строки.

---

## 6. Источник данных остатков (обязательно)

Остатки филиала **не вводятся вручную**.

```
Получено со склада
− Продано
− Возвращено покупателем (если возврат в магазин)
− Списано
± Возврат магазина на склад (уход с точки)
= Текущий остаток
```

Реализация: `StockBalance` + движения через складские сервисы.  
**Ручное изменение количества запрещено.**

Owner Direct: остаток = остаток **WAREHOUSE**; продажа списывает склад напрямую (№17).

---

## 7. Вкладка «Продавцы» (только BRANCH)

Только сотрудники этой точки:

- имя, статус, дата создания, последний вход;
- кол-во продаж, сумма, средний чек;
- кол-во запросов скидок / возвратов.

Действия Owner: добавить · заблокировать · разблокировать · сбросить пароль · изменить роль.  
Пароль **никогда** не отображается (только hash).

---

## 8. История продаж

Все продажи точки. Поля: номер · дата · время · продавец · товары · qty · скидка · подарок · итог · способ оплаты · статус.

После завершения продажа **неизменяема**.

---

## 9. История скидок

Дата · время · продавец · причина · размер · решение Owner · комментарий · время подтверждения.

---

## 10. История возвратов

Товар · qty · причина · продавец · кто подтвердил · дата · время.  
После approve — остатки по бизнес-логике (магазин или склад).

---

## 11. История ревизий (BRANCH)

Дата · время · точка · кто проводил · статус.

| Роль | Видит |
|------|--------|
| Owner | факт · ожидание · расхождение · сумма недостачи/излишков |
| Manager (проведение) | **только** введённый факт — **без** ожидания, недостачи, стоимости |

Это **обязательное** ограничение безопасности (blind count).

---

## 12. Вкладка «Запросы»

Скидки · возвраты · списания.  
Фильтры: новые · подтверждённые · отклонённые.

---

## 13. Настройки точки

Изменяемо: название · адрес · телефон · статус · рабочее время · уведомления · минимальные остатки (пороги точки).

**Удаление запрещено.** Только:

```
Активный  |  Архивный
```

Для Owner Direct: имя канала может быть защищено; логика остатков не меняется настройками филиала.

---

## 14. Особый канал владельца (обязательно)

См. полный контракт: **[№17 Owner Direct Sales](owner-direct-sales.md)**.

Кратко:

- создаётся автоматически при создании компании;
- единственный `OWNER_DIRECT` на компанию;
- без перемещений;
- продажа → сразу − склад;
- в общей аналитике — отдельная строка канала;
- упрощённый POS с правами Owner (скидка без self-approve request).

---

## 15. Журналирование (Audit Log)

Любое действие модуля → audit:

дата · время · пользователь · роль · IP (если есть) · устройство (если есть) · действие · объект · old · new · результат.

Не редактируется и не удаляется пользователями.  
Удалённые/архивные сущности: журнал сохраняется.

---

## 16. Требования к реализации (обязательно)

1. Промышленная ERP — **без** временных решений, ломающих архитектуру при росте.  
2. Desktop + Mobile, единый Design System.  
3. Роли: Owner / Manager / Seller (Seller **не** управляет разделом точек сети).  
4. Данные только через API + `lib/services` (складская логика).  
5. Любое изменение состояния: валидация → audit → отражение в аналитике, остатках, уведомлениях, истории.  
6. Заглушки UI допустимы **только** для ещё не реализованных подсистем (продажи/ревизии), с явным статусом «в разработке», но **контракт вкладок и API-полей** уже должен соответствовать этому документу.
