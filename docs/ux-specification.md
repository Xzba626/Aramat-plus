# UX Specification №3

**Проект:** ARAMAT PLUS ERP  
**Версия:** 1.0  
**Статус:** Ориентир для UI, User Flows и Business Process Specification  
**Связанные документы:** [Vision №1](vision.md), [Design System](design-system.md), [UI Blueprint №13](ui-blueprint.md), [RBAC](rbac.md)

---

## 1. Цель UX

Интерфейс должен быть максимально простым, быстрым и понятным для всех ролей.

Основные требования:

- минимальное количество кликов;
- логичное расположение элементов;
- единый стиль всех экранов;
- отсутствие перегруженности;
- одинаковое удобство на компьютере и телефоне (с учётом приоритета устройств по ролям — см. §16 и §18).

---

## 2. Типы пользователей

Система проектируется для четырёх ролей:

1. **Владелец (Owner)**
2. **Менеджер (Manager)**
3. **Кладовщик (Warehouse)**
4. **Продавец (Seller)**

После входа каждый пользователь видит только те разделы, к которым у него есть доступ.

### Приоритет устройств

| Роль | Основное устройство | Вторичное |
|------|---------------------|-----------|
| Владелец | ПК / ноутбук | Смартфон (полноценно) |
| Менеджер | ПК / ноутбук | Смартфон |
| Кладовщик | ПК / планшет / смартфон | — |
| Продавец | **Только смартфон** | ПК не целевой сценарий |

## 4. Экран авторизации

После открытия приложения пользователь видит:

- логотип ARAMAT PLUS (или логотип текущей компании из настроек);
- поле логина (email / логин);
- поле пароля;
- кнопку «Войти».

После успешного входа система определяет роль и открывает соответствующий интерфейс (Owner → Dashboard, Seller → POS/Главная продавца, Warehouse → Склад).

Регистрации нет — доступ выдаёт только владелец.

---

## 5. Главная страница владельца

Главная страница **не** должна содержать глубокую аналитику.

Она предназначена для быстрого обзора состояния бизнеса («экран утра»).

Отображаются:

- быстрые действия (новый товар, перемещение, продажа, ревизия, новый продавец…);
- сводка за сегодня с динамикой к вчера;
- количество новых уведомлений;
- количество ожидающих скидок;
- количество ожидающих возвратов;
- товары с минимальными остатками;
- последние действия пользователей;
- последние продажи;
- топ магазинов (кратко).

Глубокая аналитика — только в разделе **Аналитика**.

---

## 6. Аналитика

Раздел полностью отделён от главной страницы.

### Выбор периода

- Сегодня
- Неделя
- Месяц
- Произвольный период

### Выбор области

- Все магазины **или** конкретный магазин

### Блок «Продажи»

- выручка;
- себестоимость;
- прибыль;
- чистая прибыль;
- количество продаж.

### Блок «Расходы»

Отдельный блок. Красным цветом, каждая строка со знаком «−»:

- аренда;
- зарплата;
- прочие расходы;
- одобренные скидки.

### Итог

**Чистая прибыль** — зелёным цветом.

### Ниже

- ТОП-5 товаров;
- ТОП-5 брендов;
- ТОП-5 категорий;
- самый прибыльный магазин;
- самый прибыльный продавец.

---

## 7. Экран склада

Склад — главный источник информации (master data).

Здесь можно:

- создать товар;
- изменить товар;
- изменить себестоимость (через партии / политику);
- изменить цену продажи;
- добавить новую партию;
- изменить минимальный остаток;
- архивировать товар.

Все изменения master-данных автоматически доступны магазинам.

---

## 8. Карточка товара

Вкладки:

### Основная информация

- название, бренд, категория, тип товара, единица измерения, фотография;
- внутренний ID, артикул, штрих-код.

### Цены

- текущая цена продажи;
- себестоимость (по партиям / сводка) — **только для Owner / Manager / Warehouse**;
- история изменения цен.

### Остатки

- склад;
- остатки по каждому магазину;
- общий остаток.

### Партии

Для каждой партии: дата, количество, себестоимость, комментарий. Партии **не объединяются**.

### История

Все изменения товара.

---

## 9. Продажа (POS продавца)

Главный экран продавца. Максимально быстрый сценарий.

| Шаг | Действие |
|-----|----------|
| 1 | Поиск: название, бренд, категория, ID, артикул, штрих-код |
| 2 | Выбор товара |
| 3 | Количество / объём (мл для разливных) |
| 4 | В корзину |
| 5 | Авто-уведомление о подарке по акции (если условия выполнены) |
| 6 | Опционально: «Запросить скидку» → желаемая цена + комментарий → статус Ожидает / Одобрено / Отклонено в реальном времени. Одобренная скидка действует **только на текущую продажу**, прайс в системе не меняется |
| 7 | «Продать» → остаток ↓, аналитика, история, чек (если есть принтер) |

Целевое правило: **не более трёх действий** для типовой продажи без скидки (найти → количество → продать).

---

## 10. Передача товаров

Владелец или кладовщик выбирает:

1. Магазин назначения  
2. Товары  
3. Количество  

После подтверждения:

- остаток склада ↓;
- остаток магазина ↑;
- запись в истории;
- списание партий FIFO с сохранением себестоимости на стороне магазина.

---

## 11. Возвраты

Продавец: «Создать запрос на возврат» → продажа → товар → причина.

Владелец: одобрить / отклонить.

При одобрении: остатки ↑, аналитика корректируется, запись в журнале.

Продавец **не** оформляет возврат самостоятельно.

---

## 12. Ревизии

Этапы:

1. Выбор магазина  
2. Выбор категории (опционально)  
3. Подсчёт товаров  
4. Ввод фактических остатков  
5. Сравнение с системой  
6. Расхождения  
7. Комментарий / причина  
8. Подтверждение  
9. Акт ревизии  

---

## 13. Уведомления

Отдельный раздел. Типы:

- низкий остаток;
- запрос скидки;
- запрос возврата;
- завершение ревизии;
- новая поставка;
- ошибка системы.

Каждое уведомление: дата, время, магазин, товар (категория → бренд → название), описание.

---

## 14. История (глобальные журналы)

Независимые журналы:

- продажи;
- возвраты;
- скидки;
- изменения цен;
- изменения себестоимости;
- действия пользователей;
- складские операции;
- ревизии;
- перемещения товаров.

Для каждого: поиск, фильтры (период, магазин, пользователь), экспорт.

---

## 15. Настройки

Владелец может изменить:

- логотип и название компании;
- фирменные цвета;
- категории, бренды, единицы;
- минимальные остатки и пороги уведомлений;
- расходы магазинов (аренда, зарплата, прочие);
- правила акций;
- права пользователей.

(Согласовано с принципом универсальности платформы из Vision §21.)

---

## 16. Адаптация

Интерфейс должен хорошо работать на ПК, ноутбуке, планшете и смартфоне.

На телефоне:

- меню → боковая / нижняя панель;
- большие таблицы → карточки с раскрытием деталей.

Owner: desktop-first, но mobile полноценен.  
Seller: **mobile-first**.

---

## 17. UX-принципы

- Не более трёх действий для основной операции (типовая продажа).
- Подтверждение только для опасных действий (удаление, смена цен, возврат, сброс пароля).
- Автоматические расчёты (скидки, подарки, прибыль, остатки, расходы).
- Наглядность: зелёный — прибыль/успех; красный — расходы/предупреждения; фирменный красный — ключевые CTA бренда.

---

## 18. Интерфейс продавца (детализация)

Интерфейс продавца максимально упрощён и заточен под смартфон.

Продавец **не** использует компьютер в повседневной работе.

### Меню продавца

- Главная  
- Продажа  
- Корзина  
- История продаж  
- Запросы на возврат  
- Остатки своего магазина  
- Уведомления  
- Профиль  

### Продавец не видит

- себестоимость товаров;
- общую прибыль;
- аналитику;
- расходы магазина / сети;
- остатки других магазинов;
- настройки системы;
- управление пользователями;
- партии и закупочные цены.

---

## 19. Конфиденциальность цен

Разделение информации по ролям.

### Продавец видит

- название, бренд, категорию;
- **цену продажи**;
- остаток своего магазина (если владелец разрешил);
- акции и подарки.

### Продавец не видит

- себестоимость;
- прибыль / маржинальность;
- расходы;
- закупочные цены;
- финансовую аналитику.

Owner / Manager / Warehouse видят себестоимость и финансы согласно правам.

---

## 20. Профиль продавца

Продавец может самостоятельно изменить:

- **пароль** (обязательно);
- язык интерфейса;
- фотографию профиля.

**Логин (email)** меняет только владелец — чтобы не ломать поиск сотрудника в системе и аудит.

---

## 21. Безопасность паролей

### Создание сотрудника

Владелец:

- задаёт логин и **временный** пароль вручную; **или**
- нажимает «Сгенерировать» — система создаёт безопасные учётные данные.

### После первого входа

Сотрудник **обязан** сменить временный пароль на свой.

### Хранение

- Пароли **никогда** не отображаются владельцу после сохранения.
- Хранятся только в виде хеша (bcrypt / аналог).
- Даже администратор системы не может «посмотреть» пароль.

### Сброс

Если сотрудник забыл пароль:

1. Владелец нажимает «Сбросить пароль».
2. Задаёт новый временный пароль или генерирует его.
3. Сотрудник снова меняет пароль после входа.

Старый пароль восстановить невозможно — только сброс.

---

## 22. Привязка сотрудников к подразделениям

При создании пользователя владелец **обязательно** выбирает привязку.

### Продавец

```
Имя: Али
Роль: Продавец
Магазин: Душанбе №2
```

Доступ только к своему магазину.

### Кладовщик

```
Имя: Саид
Роль: Кладовщик
Склад: Центральный склад
```

### Менеджер

Владелец выбирает, к каким складам и/или магазинам есть доступ (один или несколько).

Без привязки продавец / кладовщик не создаётся.

---

## 23. История действий сотрудников

Для каждого пользователя — журнал действий.

Запись содержит:

- дату и время;
- пользователя;
- магазин / склад (если применимо);
- IP-адрес устройства (опционально, включать настраиваемо);
- выполненное действие;
- результат / объект (товар, сумма и т.д.).

Примеры:

```
10.08.2026 09:15 | Продавец Али | Магазин Душанбе №2
Продал | Dior Sauvage | 100 мл
```

```
10.08.2026 14:21 | Владелец
Изменил цену | Bleu de Chanel | 150 → 170 сомони
```

Любое действие на складе (добавление товара, партия, цена) фиксирует **кто** и **когда**.

---

## 24. История магазина

У каждого магазина — собственная история внутри карточки магазина  
(путь: **Магазины → [магазин]** — не путать с глобальной Аналитикой).

Вкладки карточки магазина:

- Обзор / остатки / сотрудники;
- **История продаж**;
- **История возвратов**;
- **История скидок**;
- **История поступлений**;
- **История перемещений**;
- **История ревизий**;
- **История действий сотрудников**.

Так владелец полностью прослеживает всё, что происходило именно в этом магазине.

Аналогично: у склада — своя история складских операций с указанием автора.

## 25. Следующие документы (зафиксированные предложения)

### 25.1 User Flow Specification (между UX и UI)

Подробные сценарии с переходами экранов:

- авторизация;
- оформление продажи;
- запрос / подтверждение скидки;
- возврат;
- приём поставки;
- перемещение;
- ревизия;
- создание акции;
- изменение цены;
- уведомления;
- создание / сброс пароля сотрудника;
- первый вход и смена временного пароля.

Цель — устранить логические дыры до UI и кода.

### 25.2 Business Process Specification (BPS)

После пакета документов — сквозные бизнес-процессы «от начала до конца»:

- продажа, поступление, перемещение, скидка, возврат, ревизия;
- изменение цены;
- создание магазина / продавца;
- увольнение продавца;
- восстановление пароля;
- акция;
- уведомление о низком остатке.

Для каждого процесса: шаги, участники, условия, проверки, итог.

BPS свяжет разрозненные разделы в единое поведение системы.

## Итог

UX Specification отвечает на вопрос **как пользователь работает с системой**.

Ключевые правила, которые нельзя нарушать в UI/коде:

1. Seller = smartphone, без себестоимости и финансов.  
2. Пароли только хеш; владелец сбрасывает, не «смотрит».  
3. Сотрудник всегда привязан к магазину/складу.  
4. История — глобальная и **по магазину** (вкладки карточки).  
5. Dashboard владельца = утренняя сводка; аналитика — отдельный раздел.  
6. Продажа = минимум кликов; скидки/подарки — системой.

Далее: **User Flow Specification**, затем UI Kit / экраны, параллельно — SRS/BPS по мере готовности.
